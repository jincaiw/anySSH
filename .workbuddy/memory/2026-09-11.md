### 🔴 本轮最重要发现：CSP 必须显式放行 `connect-src data:`

`@devolutions/iron-remote-desktop-rdp` 把 WASM 以**内嵌 `data:application/wasm;base64,…` 常量**打包，启动路径是
`rdp.init()` → wasm-bindgen `__wbg_init` → **`fetch(<data URL>)`** → `WebAssembly.instantiateStreaming`。
（实证：bundle 内 `B === void 0 && (B = kA)`，`kA` 即该 data URL，紧接着 `(typeof B == "string" …) && (B = fetch(B))`。）

**CSP 把 `fetch()` 一个 `data:` URL 当网络请求按 `connect-src` 校验，`'self'` 和 `*` 都不覆盖 `data:` scheme，必须显式列出。**
漏了它 → `rdp.init()` reject → RDP 落外层 `catch` → `host.appendChild(el)`（`RdpCanvas.tsx:371`）不执行 → 查看器**静默完全不挂载**。
⇒ **审计阶段草拟的 CSP（只写 `connect-src 'self' ipc: http://ipc.localhost`）若直接落地，会把 RDP 功能整体打掉，且没有一条现有 E2E 能发现**（RDP 无 fixture，`74` 号只断言卡片文案 `"RDP"`）。

## RDP 诊断修复 + 限制文档化（分支 `fix/rdp-standard-security-diagnosis`，基线 `e676bf6` main）

触发：jason 贴出 `29.1.0.122:33890` 两张连接失败截图。**该目标在当前后端下无法连接，非客户端可修** —— 解码 `hex[:32]=030000130ed000001234000201080000000000` 得 `RDP_NEG_RSP selectedProtocol=0x00000000=PROTOCOL_RDP`（标准 RDP 安全层/RC4），IronRDP 上游 `connection.rs:266-268` 硬拒绝 `is_standard_rdp_security()`。8 个 CR 变体全穷尽，连 `host+SSL(0x1)` 也回 PROTOCOL_RDP。

**与 v0.14.44 那次作废结论必须区分**（`.workbuddy/rdp-rc4-验证单.md` 顶部已有作废声明）：那次根因是 CR 构造器把 `requestedProtocols` 写成**大端**（服务端读成 `0x03000000` 非法位组合后丢连接），修于 `b634c49`/v0.14.45。**本次 CR 已是 `to_le_bytes`，响应仍显式选 PROTOCOL_RDP，证据成立。**

### 修掉的两个真实缺陷（`src-tauri/src/remote/rdp.rs`）

1. **`saw_standard_rdp` 漏判**：原仅在 `!nego_rsp` 时置位（`rdp.rs:350-352`），**显式 `NEG_RSP selected=PROTOCOL_RDP` 不置位** ⇒ 结论句消失，只剩原始变体列表。本次能出结论句纯属巧合（`host+legacy-no-nego` 变体回了裸 CC）。
   → 改为两个独立布尔 `explicit_rdp_rsp` / `ignored_negotiation`，措辞分别对应「服务端明确选了 PROTOCOL_RDP」与「服务端无视 RDP_NEG_REQ 回了裸 CC」，由纯函数 `standard_security_conclusion(bool,bool)` 生成（4 种组合可单测）。
2. **结论句位置与措辞**：原拼在 `tried` 列表**之后**，列表约 700 字符，把句子挤出连接弹窗可见区域（截图里断在 `(which`）。且原措辞称服务端 *"answers only a CR without RDP_NEG_REQ with a plain X.224 CC"*，与同屏 7 行 `NEG_RSP selected=PROTOCOL_RDP` **直接矛盾**。
   → 结论句改为紧跟 `"no X.224 variant completed TLS"` 之后、列表之前。

**测试常量改名（关键）**：`X224_CONFIRM_PLAIN` → `X224_CONFIRM_RDP`（它从来不是裸 CC，含显式 `NEG_RSP` type=2）；新增真正裸 CC 的 `X224_CONFIRM_BARE_CC`（11 字节）。**这个命名混淆正是漏判的根源。** 假服务端 helper 签名由 `&'static [u8;19]` 放宽为 `&'static [u8]` 以覆盖两种形态。

- **踩到的坑（本轮最重要的诚实性教训）**：首版用 `ps -o rss= -p <pid>` 采样并 `.unwrap_or(0)`，但**沙箱 seatbelt 禁止 `ps`**（`Operation not permitted`）⇒ 静默得到 `rss=0`，读数就成了「内存零增长」。已改为返回 `Option<u64>`：采不到时打印 `rss=unavailable ...`、明确输出「内存漂移未测量」并**跳过** RSS 断言。**「测不到」与「没增长」绝不能长得一样**——用伪造的 0 去满足断言，等于把缺口伪装成通过。
- 试过的替代方案记录（避免重走）：`libc::getrusage` 的 `ru_maxrss` 是**峰值**、且需要 `unsafe`（`MaybeUninit::assume_init`/`zeroed`）构造 `rusage`（libc 无 `Default`）⇒ 会破坏「`unsafe` 0 处」的干净结论；libc 0.2.189 的 apple 模块**没有** `task_info` 声明（只有 `mach_task_basic_info` 结构体与常量），走 mach API 需自写 `extern "C"`；Darwin 的 `kinfo_proc` 不含 rss，`sysctl` 路线不通。⇒ 结论：**保留 `ps`**（普通终端可用），仅把失败显式化。
