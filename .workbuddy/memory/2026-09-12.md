### 本轮最有复用价值的三个方法论点

1. **「什么都没发生」不是充分证据。** 验 `autoUpdate=false` 时，若更新检查因网络失败根本没跑，观测结果与「标志生效」**完全一样**。必须做**双向对照**（置 `true` 确认真的会自升级）才能封住这个推理缺口。**后续任何「某开关抑制了某行为」的验证都适用。**
2. **「关掉自动更新」关的是静默安装，不是联网。** `checkOnStartup` 在 `autoUpdate=false` 时仍会请求 `latest.json`，只是改为弹窗。凡涉及「关掉 X 就没有出站」的推断都必须抓包证实，不能凭开关推断。
3. **旧版回滚测不出 schema 闸门。** 闸门是 v0.15.0 才引入的，且 0.14.46 与 0.15.0 **同为 schema 20** ⇒ 回滚**零迁移**。原手册「旧版应提示库版本更高」是**事实错误**，已修正为 A（回滚本身）/ B（人为造 `schema_version=21`）两段。

## 续：E2E 编排被上游打断——查出并修复（`ba5b8d1`）

### 起因：查文档提交为什么是红的

推完文档后核对 CI，发现**两条更早的纯文档提交也是红的**（此前只记到 25b2a92、2c31fd2）。查下去发现失败根本不是一类东西：

| 提交 | 现象 | 性质 |
|---|---|---|
| `25b2a92` | 1 shard，`19-sftp-refresh` | 环境性 |
| `2a63485` | 2 shard，`38-edit-auth-type` + `04-connect-key`（publickey 被拒） | 环境性 + **未解释** |
| `7b57755`、`7e8d3b8` | **4 shard 全挂，0 个 spec 运行** | **确定性编排故障** |

### A 类：MinIO 镜像从 Docker Hub 被移除（已修）

`make e2e-pull` 每次都挂在 `pull access denied for minio/minio`。**区分「仓库被删」与「限流」是关键**——两者都是 `docker pull` 失败，含义完全不同：

- 取 registry token 后解 JWT 的 `access` 声明：`granted_access=[]` + manifest `401` ⇒ **仓库未公开/已删**（限流是 429 / `toomanyrequests`）。
- 命名空间列表交叉验证：`minio` 命名空间下 20 个公开仓库里**已无 `minio`、`mc`**。
- 搜索确认：MinIO 于 **2025-10-23** 停止发布社区版镜像（Docker Hub 与 Quay 都曾下线）。
- `quay.io/minio/{minio,mc}` **仍返回 200**（冻存的最后一版）⇒ 修复只需换 registry 前缀。

**必须带阳性对照**：同一份探测代码先打 `library/alpine`、`library/busybox` 得 200，才敢信那两个 401。差点又栽在"探测器自己坏了"上。

用户选择换 quay.io（推荐项）。Chainguard 的免费镜像（`cgr.dev/chainguard/{minio,minio-client}`）也 200，但**是 distroless、没有 shell**，`minio-seed` 的 `entrypoint: sh -c` 会直接跑不起来 ⇒ 不是"改个前缀"就能换，已如实告知。

### B 类：环境性抖动（未修，也不该靠改测试修）

`ba5b8d1` 同一二进制跑三次：attempt 1 三红 → attempt 2 一红 → attempt 3 **全绿（75/75）**。**失败 spec 每次都在换**。

**新增一条比「重跑才绿」更硬的论证**：分片是**确定性 round-robin**（`wdio.conf.ts` 排序后 `i % 4`），所以每个 shard 的 spec 集合**固定**。把近期所有失败过的 spec 映射回 shard，结果是**分散在全部 4 个 shard、且都落在预期 shard 里**——若是某个 spec/shard 有真实缺陷，失败应当**集中且每轮复现**。这条比"换个 spec 失败"更难反驳。

根因候选（有日志支撑）：容器内 `libEGL DRI3 error` ⇒ WebKitGTK 软渲染；**runner 镜像没装 mesa 软件光栅化后端、也没设 `WEBKIT_DISABLE_COMPOSITING_MODE`/`LIBGL_ALWAYS_SOFTWARE`**，所以回退是听天由命的。**根治方向是让渲染确定化，不是调大等待预算**——已写进报告作为未做项。

### C 类：未解释，且推翻了此前的错误判断

`04-connect-key` 报 `publickey ssh-ed25519 rejected`。**决定性证据**：同 shard 的 entrypoint 就绪门在 **15:27:47** 打印 `sshd-key accepts the test key`，失败在 **15:29:01**——**74 秒后**；且 spec 与就绪门用的 host/port/user/key **完全相同**（已核 `USER_NAME`、`PUBLIC_KEY_FILE` 与 spec 默认值）。

⇒ **不是就绪竞态**。报告里"该类已由 `0fc493d` 修复"的说法**不成立**（就绪门当时是通过的）。这是本项目**第一个被自己的实测推翻的既往结论**——已按证据改写，并保持"不判定为通过"。

### 另一处被推翻的论断

报告 §10 原写「纯 Markdown 的报告修订**不重跑 CI**」——**错的**。`ci.yml` 对 `main` 每次 push 都无条件运行（三条纯文档提交的 run 都跑了且都红）。已改写，并补上后果：**那几条提交无法用"重跑旧 run"回头验证**（A 类是编排层面的，重跑同样提交仍卡在镜像拉取），等价证据改为在**源码完全相同**的 `ba5b8d1` 上取到的全绿。

### 方法论点（可复用）

1. **「0 个 spec 运行」与「spec 失败」是两种病**：前者是编排/基础设施，重跑永远不会好；后者才可能是抖动。看到 4 个 shard 同时挂，先怀疑拉取/启动阶段，不要直接归入"抖动"。
2. **确定性分片可以让归因变硬**：把失败 spec 映射回 shard，检查"是否集中"。分散 + 每轮换点 ⇒ 环境；集中 + 复现 ⇒ 真缺陷。
3. **推翻自己的旧结论要留痕**：把"此前判断不成立"写进报告并给证据，比悄悄改掉更有价值。
4. 探测外部资源（registry/端点）**一律先跑阳性对照**，否则分不清"目标坏了"和"探测器坏了"。

## 续：v0.15.1 第一次发布丢 Linux 产物 —— 发布流程的 sed 吃掉了依赖要求

### 现象

`v0.15.1` 第一次构建：macOS(Intel/Apple Silicon) 与 Windows **全 success**，**Linux failure**。因为不是"构建失败"而是"少一个平台"，很容易被当成上游抖动放过去。

### 根因（两个条件叠加）

```
error: failed to run custom build command for `rfd v0.15.4`
thread 'main' panicked at rfd-0.15.4/build.rs:14:17:
You need to choose at least one backend: `gtk3` or `xdg-portal` features
```

注意是 **rfd 0.15.4**，而我声明的是 `0.16`。本地依赖图里只有 `0.16.0`——差别只能来自 release 流程对 Cargo.toml 的改写：

```bash
sed -i.bak "s/^version = \".*\"/version = \"$VERSION\"/" src-tauri/Cargo.toml
```

这条 sed **分不清包版本与依赖要求**。我写的 `[target.'cfg(...)'.dependencies.rfd]` 表下恰好有一行独立的 `version = "0.16"` ⇒ 发布时被改成 `version = "0.15.1"` ⇒ 要求变成 `^0.15.1` ⇒ 解析出 rfd 0.15.4 ⇒ 其 build.rs 在 Linux 上要求 gtk3/xdg-portal feature ⇒ panic。**macOS/Windows 不受影响，因为该检查只在 Linux 生效。**

### 修法（两层，任一层都能挡住这次）

1. **Cargo.toml**：改成内联 `rfd = { version = "0.16", default-features = false }`（表头用 `[...dependencies]`）。该行不以 `version` 开头 ⇒ 任何模式的 sed 都看不见。
2. **release.yml**：锚定占位符值 `s/^version = "0\.0\.0-dev"/version = "$VERSION"/` + **失败即 `::error::` 退出**。

### ⚠️ 差点自伤第二次：`0,/re/` 是 GNU 扩展

我第一版修法用了 GNU 惯用法 `0,/^version = \"/s//.../`，本机实测 **BSD sed 直接报 `no previous regex`**。而这一步位于 `build` job 的 `${{ matrix.platform }}` —— **macOS 与 Windows runner 也在跑它**。若没先测，会把三个平台的发布全弄挂。⇒ **凡 workflow 里改文本的 sed，必须按 BSD/POSIX 子集写，并在本机用 BSD sed 实测。**

### 验证方式（可复用的 30 秒自检）

把注入逻辑在本地跑一遍，再看**只有一处** `^version = `，并用 `cargo metadata` 确认依赖要求没被改：

```bash
cp src-tauri/Cargo.toml /tmp/ct.orig
sed -i.bak "s/^version = \"0\.0\.0-dev\"/version = \"9.9.9\"/" src-tauri/Cargo.toml
grep -n '^version = ' src-tauri/Cargo.toml    # 只应有一行
cd src-tauri && cargo metadata --locked --no-deps --format-version 1 >/dev/null && echo OK
cp /tmp/ct.orig ../src-tauri/Cargo.toml
```

### 处置

`gh release delete v0.15.1 --yes --cleanup-tag` 清掉坏 draft 与远端 tag，本地 `git tag -d`，在含修复的 `7053acf` 上重打 `v0.15.1`。**`v0.15.1` 从未对外发布过（draft、0 资产），所以复用同一版本号是安全的**；更新端点读 `releases/latest`，仍指向 v0.15.0，用户侧无感。

这两个坑（表头吞键、sed 吃依赖行）已写进 `anyssh-release-flow` 技能。
