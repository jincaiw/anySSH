# anySSH 发布前验收标准与提示词

本标准用于每次正式版或预发布版本的发布决策。它描述验收范围和通过条件，不代表当前提交已经通过。每次验收必须记录实际提交 SHA、版本/tag、CI 运行链接和证据；旧审计结论不可直接沿用。

项目是基于 Tauri v2 的桌面客户端，前端使用 React/Vite/TypeScript，后端为 Rust。主要产品面包括 SSH 终端、连接管理、SFTP 文件管理与传输、S3 兼容存储、端口转发、远程桌面（RDP/VNC）、Telnet/串口，以及设置、历史记录、更新器和中英文界面。

## 1. 发布结论

验收报告必须给出当前阶段及以下结论之一。验收有两个阶段，不能把 tag 构建后才可取得的证据当作打 tag 前的前置条件：

- **GO（可打候选 tag）**：所有打 tag 前的阻断项通过，代码提交和同 SHA CI 已核实，人工验收门禁完成或按约定接受并留档。
- **GO（可公开发布）**：候选 tag 的跨平台构建成功；Release 资产、版本、更新清单和签名已核对；发布说明准确；不存在未处置的阻断风险。
- **CONDITIONAL GO**：只适用于有明确缓解的非阻断问题；每项都需写明影响、接受人、负责人、完成时点和是否允许公开发布。不得把未验证项目写成通过，也不得用此结论绕过 P0/P1 或本标准标明的阻断项。
- **NO-GO**：存在未解决的 P0/P1、关键验收缺证、必需 CI 失败、产物与源码不一致或更新签名不可验证。

状态用语统一为：**已验证**、**验证失败**、**需要人工验证**、**不适用**。每项“已验证”都需给出可复查的证据（命令及结果、CI job/运行链接、截图或人工操作记录）。

## 2. 阻断门禁

打候选 tag 和公开发布前逐项核对。任一适用于当前阶段的阻断项失败或没有证据时，不得给出对应 GO 结论。

### A. 源码与版本

- [ ] 明确仓库、发布分支、目标版本/tag、候选提交完整 SHA、最近正式版 tag。
- [ ] 工作区无意外未提交改动；发布提交已在预期远端；tag 指向经审验提交。
- [ ] 不存在冲突标记、意外生成文件、误提交密钥/令牌/私钥、未解释的子模块/gitlink 或构建所需文件缺失。
- [ ] `package.json`、`src-tauri/tauri.conf.json`、`src-tauri/Cargo.toml` 的版本策略与 `.github/workflows/release.yml` 的 tag 注入逻辑相符；版本占位符若为设计行为，须验证 release workflow 会正确注入。
- [ ] README、许可、隐私/安全说明、更新说明与本版本实际能力和支持平台一致。

### B. 自动化质量门禁

在**候选 SHA**上确认 CI 成功，不能用相近提交或旧 run 代替：

- [ ] 前端依赖按 lockfile 安装成功；`pnpm build`（TypeScript 检查 + Vite 生产构建）成功。
- [ ] `pnpm test` 成功；检查测试发现器覆盖的测试文件/用例数、失败数、skip/todo/only 情况，并对异常变化作解释。
- [ ] Rust `cargo fmt --all --check`、`cargo clippy --all-targets -- -D warnings`、`cargo test` 成功。
- [ ] CI 中依赖/安全审计门禁成功；新 advisory、豁免和过期豁免均有明确处置记录。
- [ ] E2E 工作流所有分片/必需 job 成功；未运行或不适用的项目需说明原因和替代证据。
- [ ] 若本地环境不完整、命令结果不稳定或依赖受限，明确标注“需要人工验证”，以同 SHA 的 CI 作为证据，不得将本地失败误判为产品失败或忽略 CI 失败。

### C. 产品关键路径

按代码、自动化覆盖和可运行应用证据核对。自动化覆盖不能替代需要真实系统/网络的手工验证。

- [ ] 启动、首次使用、窗口/标签切换、关闭与重启行为正常；设置持久化有效。
- [ ] SSH：密码及密钥认证、主机指纹确认/拒绝、断线/重连、终端输入输出、窗口尺寸变化、剪贴板、搜索/主题和会话关闭清理。
- [ ] 连接管理：新增/编辑/删除主机与分组、快速连接、导入 SSH config、凭据与敏感字段处理。
- [ ] SFTP：目录浏览/刷新、上传/下载、冲突处理、重命名/删除/新建、取消与失败恢复、大文件或长传输状态；连接断开时状态一致。
- [ ] S3：兼容端点连接、桶/对象浏览、上传/下载/删除、分页或错误处理；敏感凭据不进入日志或界面错误信息。
- [ ] 端口转发：创建、启停、冲突/无效配置报错、会话断开后清理。
- [ ] RDP/VNC、Telnet、串口：仅当本版本宣称支持或相关代码有改动时，验证连接、显示/输入、断开清理及失败提示；标明真实设备/服务器和平台。
- [ ] 更新器：旧版发现新版本、签名校验、下载/安装或重启流程、失败时回滚/安全提示。无可用签名或升级环境时列为人工阻断项。
- [ ] 中英文关键页面无缺失/错位/截断；语言切换有效，i18n parity 检查成功。
- [ ] 错误、空状态、加载状态和破坏性操作确认均可理解；无明显布局、输入、键盘操作或可访问性回归。

对未改动且风险低的路径可采用既有可靠自动化作为回归证据，但需指出具体测试。涉及认证、传输、升级、数据删除或远程桌面改动时，至少对受影响路径进行真实 GUI/端到端验收。

### D. 安全、隐私与数据

- [ ] 检查本次改动涉及的 Rust 命令权限、Tauri capabilities、CSP、WebView 与远程输入边界。
- [ ] SSH 主机密钥校验、凭据存储/传递、日志脱敏、临时文件清理和错误信息没有被削弱。
- [ ] 依赖审计结果及豁免与当前 lockfile 对应；新漏洞按可达性、影响、修复方案和风险接受人记录。
- [ ] 升级/迁移不会无提示丢失用户连接、设置、历史记录或本地数据；备份/恢复路径在相关改动时验证。
- [ ] 无真实密钥、签名私钥、访问令牌或用户数据进入源码、日志、发布包或验收截图。

### E. 跨平台构建与发布资产

- [ ] `.github/workflows/release.yml` 的平台矩阵与项目承诺一致；每个平台/架构所需安装包和 portable 包构建成功。
- [ ] 在 macOS、Windows、Linux 的干净环境/虚拟机安装或解压启动；检查应用名称、图标、版本、权限、卸载/清理和首次启动提示。
- [ ] Windows WebView 离线安装模式、macOS 架构/签名公证要求、Linux 系统依赖及 portable 包说明与实际产物一致（适用时）。
- [ ] **打 tag 前**：release workflow 的平台矩阵、版本注入、签名密钥配置与产物命名规则已审阅；尚不存在的产物标为待 tag 后检查。
- [ ] **tag 构建后、公开发布前**：Release 资产名称、平台/架构、数量、大小、校验和与构建 job 对应；无缺失、重复或错误版本产物。
- [ ] Tauri updater 的 `latest.json` 版本、下载 URL、平台条目和 `.sig` 文件齐全；使用对应公钥验证签名，并完成至少一次旧版到候选版的端到端升级。
- [ ] Release notes 准确覆盖用户可见变化、破坏性变更、已知问题、下载/升级说明；没有误导的“已验证”声明。

## 3. 风险分级和例外

- **P0**：可导致数据/凭据泄漏、任意代码执行、关键数据损坏，或发布/升级供应链完整性失效。立即 NO-GO。
- **P1**：主要功能不可用、关键平台无法安装/启动、认证/传输/更新关键路径失败，或必需质量门禁失败。立即 NO-GO。
- **P2**：有明确缓解方式的非关键缺陷、部分边缘路径回归。只有经发布负责人明确接受、披露影响并列出修复版本后，才可 CONDITIONAL GO。
- **P3**：文档/视觉/低影响卫生问题。可记录到后续版本，不应掩盖更高级别问题。

风险条目必须包含：级别、受影响版本/平台/路径、复现步骤、影响、证据、缓解方式、处置人和决定。安全风险不得只以“暂时无法复现”关闭。

## 4. 可复用验收提示词

将下方提示词交给 Codex，在项目仓库中按候选提交执行。填写方括号中的信息；未提供的信息让验收者从仓库和 Git/CI 证据中核实，不得臆造。

```text
请对当前 anySSH 仓库执行一次发布前验收审计，并按 docs/pre-release-acceptance-standard.md 的标准给出可复查报告。

验收对象：
- 目标版本/tag：[版本号或“尚未打 tag”]
- 候选分支：[分支名]
- 本次特别关注/变更范围：[功能、缺陷修复或“请从 diff 总结”]
- 指定的人工环境/服务器：[如无写“无”]

执行要求：
1. 先确认仓库路径、工作区状态、分支、HEAD 完整 SHA、远端差异、最近正式版 tag，以及候选 tag（如果存在）实际指向；不要改写、暂存、提交、推送、打 tag、发布 Release 或改动生产数据。
2. 阅读项目说明、与本次变更相关的代码和测试、CI 与 release workflow、验收标准；结合 diff 评估风险和受影响路径。把当前观察到的事实与历史审计记录分开，不能沿用旧报告中的版本、计数、CI 结果或结论。
3. 收集自动化证据：前端 `pnpm build`、`pnpm test`；Rust `cargo fmt --all --check`、`cargo clippy --all-targets -- -D warnings`、`cargo test`；仓库配置的安全审计、E2E 和同 SHA CI 结果。优先使用项目已有脚本/workflow。只有在依赖已安装且环境可信时才运行本地命令；环境限制要如实说明并改查同 SHA CI，不要为获得绿灯修改测试、断言、超时或门禁。
4. 检查 SSH、SFTP、S3、端口转发、远程桌面、Telnet/串口、设置/i18n、更新器等适用关键路径。按本次 diff 和风险决定必须做的 GUI/真实服务器验证；无法实际操作的项目明确标“需要人工验证”，给出具体步骤和通过条件，不能伪称已验证。
5. 检查安全/隐私、依赖 advisory、敏感信息、跨平台构建矩阵、release 资产、`latest.json` 与更新签名。只有能够读取实际 CI/Release 证据时才报告其状态。候选 tag 尚不存在时，不能声称产物/更新器已验证。
6. 每个结论都附证据：命令和摘要、文件路径/行号、测试名称、CI job/run 链接、资产名称，或人工操作记录。区分“代码检查”“自动化验证”“真实运行验证”。记录未覆盖范围和证据局限。
7. 仅审计，不修复代码或改变发布状态。不得泄露密钥；发现疑似密钥时只指出文件和类型，不复制其值。

报告格式：
- 审计对象：仓库、分支、完整 SHA、版本/tag、基线版本、工作区状态、审计时间
- 总结：GO / CONDITIONAL GO / NO-GO，附简短理由
- 阻断门禁表：标准项、状态、证据、缺口/责任人
- 自动化结果：命令/CI job、实际结果、测试计数、失败/skip/only
- 变更影响与关键路径矩阵：功能、验证方式、结果、证据
- 风险清单：P0–P3，含复现、影响、缓解和处置建议
- 跨平台/安装包/更新器/发布说明检查
- 必须完成的人工验收清单：操作步骤、环境、通过条件、证据记录方式
- 发布前剩余条件和明确的最终判断

不得把“没有发现问题”写成“所有功能均已验证”。任何阻断项缺证或失败都必须反映在最终结论中。
```

## 5. 每次验收归档

建议每次发布将报告另存为 `docs/pre-release-acceptance-<版本>-<日期>.md`，记录候选 SHA 和证据链接。不要覆盖历史报告；正式发布后可补记最终 tag、Release 资产及更新验证结果。
